Close allocation logging/ordering gaps, fix Desktop order line numbering,
fix toolbar selection-state bug across the app

Allocation event logging (usp_allocate_order, usp_cancel_allocation,
usp_deallocate_order, usp_reallocate_line + SqlOutboundCommandRepository):
- All four now surface which unit(s)/SSCC/SKU they actually affected in
  their result sets, not just the order ID - via OUTPUT clauses on the
  multi-unit SPs (allocate, deallocate) and extra result columns on the
  single-unit ones (cancel, reallocate)
- Closes a real gap: searching the Event Log by SSCC previously found
  Inbound.ReceiveLine but not Outbound.AllocateOrder/CancelAllocation for
  the same unit, since the payload never mentioned it
- Verified end-to-end against live allocation-strategy testing: search by
  SSCC now surfaces the full allocate/deallocate history in one place

Allocation strategy tiebreak (usp_allocate_order, usp_reallocate_line):
- FEFO and NONE had no secondary sort when multiple units shared the same
  BBE - which unit won was whatever order SQL Server happened to return
  matching rows in, not a guaranteed rule (FIFO/LIFO were never at risk -
  their sort key is created_at, which is never actually tied)
- Added created_at ASC as the explicit tiebreak for FEFO/NONE
- Verified deterministic across three separate identical-setting runs
  before and after: same units, same order, every time

Desktop order line numbering (CreateOrderForm):
- OrderLineDto.LineNo was never set when building lines from the Desktop
  "New Order" form, silently defaulting to 0 for every line
- For a single-line order this just showed line_no = 0; for a multi-line
  order every line collided on the same (order_id, line_no) unique
  constraint, so the Desktop app could not create multi-line orders at
  all - failed with a generic, unrelated-looking error
- Now assigns 10/20/30... matching the convention used everywhere else

Toolbar selection-state bug (14 views across Views/):
- Symptom: a single auto-selected row on view load looked selected but
  action buttons (Allocate order, etc.) stayed disabled until Refresh
- Root cause had two layers, both fixed:
  1. Bind()/ApplyFilter() rebinding the grid without re-syncing toolbar
     state afterward - relied entirely on SelectionChanged firing
     reliably, which it doesn't on the initial auto-select during data
     binding (OutstandingOrdersView, InboundView, PartiesView,
     ShipmentsView, TasksView, InventoryView, EventLogView)
  2. MainForm.ShowView() adds the view to the panel - which fires Load
     synchronously - before calling ConfigureToolbar(), so the very
     first data bind runs before the toolbar buttons even exist;
     nothing re-synced them once ConfigureToolbar() finally created
     them (all 14 IToolbarAware views except SessionsView, which
     already had the right pattern and was the template for the fix)
- Verified fixed against the exact single-row Outstanding Orders case
  that surfaced it
