Allocation audit enrichment, customer shelf-life management,
RBAC gap fixes and object preservation, session/event-log hardening

Allocation logging enrichment (usp_allocate_order, usp_reallocate_line,
SqlOutboundCommandRepository):
- Every allocated unit's log entry now carries its own BestBeforeDate and
  the RequiredMinDays that applied to it, plus DeliveryDate and
  AllowShelfLifeOverride at the top level - every branch (success and
  failure) produces the same consistent shape, not just the happy path
- Fixes a real gap: a shelf-life-driven allocation decision was previously
  unreconstructable from the trace log alone without live narration

Customer shelf-life management (new feature, full stack):
- Schema: nullable minimum_remaining_shelf_life_days on inventory.skus,
  new inventory.customer_shelf_life_requirements table (customer+SKU
  override, cascades customer+SKU -> SKU default -> 0 at allocation time)
- usp_set/delete_customer_shelf_life_requirement (RBAC-gated on
  materials.manage, reused rather than a new dedicated key)
- New Desktop screen (Inventory -> Customer shelf life): grid, add/edit/
  delete, Add/Edit/Delete gated by permission with disable-not-hide
  convention (PermissionGating.GateBy)
- SkuEditForm extended with the SKU-level default field; MaterialsView
  and SkuAuditView both extended to show it (audit trail required
  extending Sku.Update's Before/After payload and v_sku_changes'
  JSON_VALUE extractions, not just adding a grid column)
- Verified end-to-end across many threshold values: boundary inclusion/
  exclusion, FEFO interaction, multi-lot cascading, customer-override
  precedence over the SKU default, and correct fallback on override
  deletion - all confirmed against real allocation runs, not just reasoned
  through

RBAC: real gaps found and fixed, real objects recovered
- auth.fn_has_permission, auth.fn_is_system_user, auth.v_user_permissions
  were all live and load-bearing in the database (the entire Phase 2c/2d
  permission pipeline actually works) but existed nowhere in the repo -
  same "created directly in SSMS, never scripted" pattern as the SQL
  Agent jobs found earlier. All three now saved under 030_auth/
- manager was missing settings.write, materials.manage, zones.manage,
  storage_types.manage, bins.manage - audited the full permission list
  against manager's actual grants and added the ones matching "elevated
  warehouse access" (kept users.manage, sessions.terminate_all, and
  clients.manage admin-only as a deliberate call, not an oversight)
- Verified by logging in as manager and confirming both settings and the
  new shelf-life screen are actually usable, not just seeded correctly

Session lifecycle hardening:
- usp_session_cleanup: TRY/CATCH added and contained internally (this SP
  is called inline by every login attempt, not just the 10-minute Agent
  job, so a failure here must never propagate and break login itself);
  cursor cleaned up defensively on error; failures logged
- usp_session_touch: session.expired now logged via audit.usp_log_event,
  matching its sibling usp_login in the same file - previously a session
  could expire via heartbeat with zero record of it anywhere

Unified event log (audit.v_all_events):
- New view unions audit.trace_logs with audit.audit_events (deliberately
  excludes auth.session_events, which stays a specialised, directly-
  queried session-state-machine log)
- EventLogView extended: new Source column + filter dropdown (mirrors the
  existing Level filter), Result column unified to prefer the granular
  ERRAUTH/SUCAUTH-style code over the coarser table-level status word
- Fixed a real bug found while wiring this up: the correlation-ID
  click-to-filter feature only ever worked for trace_logs rows (JSON-
  parsed out of a nested shape that audit_events rows don't have) - now
  uses the real correlation_id column from both sources directly

Expiry / write-off foundation, SQL Agent jobs:
- EX status, SCR terminal state, usp_run_expiry_sweep (self-logs, since
  it has no C# caller to log on its behalf) and usp_write_off_unit
  (single-unit foundation; documented Disposal Order workflow deliberately
  out of scope)
- Original session-cleanup job script recovered and preserved; new expiry-
  sweep job added using a portable ORIGINAL_LOGIN() owner and a dynamic
  SYSTEM-user lookup rather than a hardcoded ID (safe across reset-db,
  where IDENTITY values aren't stable)
- Deliberately kept outside Database/Scripts/ - these are one-time,
  manually-run setup scripts, not part of the automated reset cycle
  (documented in Database/Jobs/README.md)

Known open item, deliberately deferred: two coexisting conventions for
how SPs receive session context (explicit @user_id/@session_id parameters
vs. reading SESSION_CONTEXT() directly) still exist side by side. Found
that SqlConnectionFactory.CreateForCommand already sets full session
context on every connection unconditionally, so both patterns are safe
today - this is a consistency question, not a correctness risk. Next
session's first task.
